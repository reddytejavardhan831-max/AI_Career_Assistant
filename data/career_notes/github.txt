GITHUB & GIT — COMPLETE KNOWLEDGE BASE

=====================================================
1. WHAT GIT AND GITHUB ARE (AND WHY THEY MATTER)
=====================================================
Git is a distributed version control system that tracks changes to code over time, allowing multiple people to collaborate on the same codebase without overwriting each other's work. GitHub is a cloud-based hosting platform for Git repositories that adds collaboration features on top of Git itself: pull requests, issue tracking, code review, CI/CD integration (GitHub Actions), and project management tools.

Why it matters for developers:
- Every professional software team uses version control — it's a non-negotiable baseline skill, not an optional extra.
- It enables safe experimentation (branches) without risking the main, working codebase.
- It provides a complete history of changes, making it possible to understand why code changed, revert mistakes, and collaborate asynchronously across time zones.
- A well-maintained GitHub profile with real projects and contributions is one of the strongest signals recruiters and hiring managers look for, especially for candidates without extensive formal work experience.

=====================================================
2. CORE GIT CONCEPTS
=====================================================
- Repository (repo): a project folder tracked by Git, containing your files plus the full history of changes.
- Commit: a snapshot of changes at a point in time, with a message describing what changed and why.
- Working directory, staging area, and repository: the three states a change moves through — you edit files (working directory), stage the specific changes you want to include (`git add`), then commit them (`git commit`) to save that snapshot permanently in history.
- Branch: an independent line of development, allowing you to work on a feature or fix without affecting the main codebase until it's ready.
- HEAD: a pointer to your current position in the commit history (usually the tip of your current branch).
- Remote: a version of your repository hosted elsewhere (e.g., on GitHub) that you can push to and pull from.
- Clone: creating a local copy of a remote repository.
- Fork: creating your own copy of someone else's repository on GitHub, commonly used to contribute to projects you don't have direct write access to.

=====================================================
3. ESSENTIAL GIT COMMANDS
=====================================================
Setup & Basics:
- `git init` — initialize a new Git repository in the current folder.
- `git clone <url>` — copy a remote repository to your local machine.
- `git status` — see which files are staged, unstaged, or untracked.
- `git add <file>` / `git add .` — stage specific files or all changed files for the next commit.
- `git commit -m "message"` — save a snapshot of staged changes with a descriptive message.
- `git log` — view commit history; `git log --oneline` for a condensed view.

Branching & Merging:
- `git branch` — list branches; `git branch <name>` — create a new branch.
- `git checkout <branch>` or `git switch <branch>` — switch to a different branch.
- `git checkout -b <branch>` — create and switch to a new branch in one step.
- `git merge <branch>` — merge another branch's changes into your current branch.
- `git rebase <branch>` — reapply your commits on top of another branch, producing a cleaner, linear history (use cautiously on shared branches).

Working with Remotes:
- `git remote add origin <url>` — link a local repo to a remote one.
- `git push origin <branch>` — upload local commits to the remote repository.
- `git pull` — fetch and merge changes from the remote into your current branch.
- `git fetch` — download remote changes without merging them automatically (safer for reviewing before merging).

Undoing Changes:
- `git restore <file>` — discard unstaged changes to a file.
- `git reset <file>` — unstage a file without discarding its changes.
- `git reset --hard <commit>` — reset the branch to a previous commit, discarding all changes after it (use with caution — this is destructive).
- `git revert <commit>` — create a new commit that undoes a previous commit, preserving history (safer than reset for shared branches).
- `git stash` — temporarily save uncommitted changes without committing, so you can switch branches cleanly; `git stash pop` to restore them later.

Inspecting & Comparing:
- `git diff` — see unstaged changes; `git diff --staged` — see staged changes not yet committed.
- `git blame <file>` — see who last modified each line of a file and in which commit.

=====================================================
4. BRANCHING STRATEGIES & WORKFLOWS
=====================================================
- Feature branching: creating a new branch for each feature/bug fix (e.g., `feature/user-auth`, `fix/login-bug`), merging back into main once complete and reviewed.
- Git Flow: a more structured model with dedicated `develop`, `feature`, `release`, and `hotfix` branches — common in larger, release-cycle-driven teams.
- Trunk-based development: developers commit small, frequent changes directly to (or very close to) a single main branch, often paired with feature flags — common in teams practicing continuous deployment.
- Naming conventions matter for team clarity: prefixes like `feature/`, `bugfix/`, `hotfix/`, `chore/` help communicate intent at a glance.
- Protecting the main branch: requiring pull requests and passing checks before merging into `main`/`master` is standard practice on professional teams to prevent broken code from reaching production.

=====================================================
5. PULL REQUESTS & CODE REVIEW
=====================================================
- A Pull Request (PR) proposes merging changes from one branch into another, giving teammates a chance to review, comment, and request changes before merging.
- Writing a good PR description: explain what changed, why, and how to test it — screenshots/GIFs are valuable for UI changes.
- Keep PRs small and focused on a single change — large PRs are harder to review thoroughly and more likely to introduce bugs that slip through.
- Responding to review feedback professionally and promptly is a core collaboration skill, not just a technical one.
- Resolving merge conflicts: when two branches modify the same lines differently, Git can't auto-merge — you manually edit the conflicting file to decide the final content, then stage and commit the resolution.
- Squash merging vs regular merging vs rebase merging — different strategies for how a PR's commits appear in the target branch's history; teams typically standardize on one approach.

=====================================================
6. GITHUB-SPECIFIC FEATURES
=====================================================
- Issues: tracking bugs, feature requests, and tasks, often linked directly to PRs that resolve them.
- GitHub Actions: automate workflows (CI/CD) — running tests, linting, and deployments automatically on events like a push or PR.
- README.md: the front page of a repository — should clearly explain what the project does, how to set it up, and how to use it; often the first thing a recruiter or collaborator looks at.
- .gitignore: specifies files/folders Git should not track (e.g., `node_modules/`, `.env`, build artifacts) — critical for not committing secrets or unnecessary bulk files.
- GitHub Pages: free static site hosting directly from a repository, commonly used for portfolios and project documentation.
- Releases and tags: marking specific commits as versioned releases (e.g., v1.0.0) for tracking deployable milestones.
- Discussions and Wiki: for community Q&A and extended documentation beyond the README.
- Contributing to open source: forking a repo, making changes on a branch, and submitting a PR back to the original project — the standard open-source contribution workflow.

=====================================================
7. BUILDING A STRONG GITHUB PROFILE
=====================================================
- Pin your 4-6 best, most polished projects to your profile — quality and completeness matter far more than quantity.
- Write clear, informative READMEs for every project: what it does, tech stack used, how to run it locally, and (ideally) a live demo link or screenshots.
- Commit regularly with meaningful, descriptive commit messages rather than vague ones like "fix" or "update" — this reflects real engineering discipline to anyone reviewing your history.
- Avoid committing sensitive data (API keys, passwords, `.env` files) — use `.gitignore` from the start of a project, and if a secret is accidentally committed, rotate it immediately (removing it from history alone isn't sufficient once it's been pushed).
- Keep your contribution graph authentic — don't artificially inflate it; consistent, genuine activity over time is what actually signals engagement to reviewers who look closely.
- Consider contributing to open-source projects, even small documentation or bug fixes — it's real evidence of collaboration skills beyond solo projects.

=====================================================
8. COMMON INTERVIEW/PRACTICAL TOPICS
=====================================================
- Explain the difference between `git merge` and `git rebase`, and when you'd use each.
- What is a merge conflict, and how do you resolve one?
- Explain the difference between `git fetch` and `git pull`.
- What is the difference between `git reset` and `git revert`? Why is one considered safer for shared branches?
- How would you undo a commit that's already been pushed to a shared branch?
- Explain what a `.gitignore` file does and why it matters.
- What's the difference between a fork and a branch?
- Walk through your typical Git workflow when starting a new feature.
- What would you do if you accidentally committed a secret/API key to a public repository?

=====================================================
9. CAREER ADVICE
=====================================================
- Treat your GitHub profile as part of your resume — many recruiters and hiring managers check it directly, especially for junior/mid-level candidates.
- Get comfortable with Git from the command line, not just a GUI tool — interviewers and real collaborative workflows often expect command-line fluency, and it deepens your actual understanding of what's happening under the hood.
- Practice resolving merge conflicts deliberately (e.g., by having two branches deliberately edit the same lines) rather than only encountering them for the first time under real project pressure.
- Learn your team's/company's specific branching and PR conventions quickly when starting a new job — these vary meaningfully between organizations even though the underlying Git concepts are universal.

=====================================================
10. HOW TO IMPROVE YOUR GIT/GITHUB SKILLS
=====================================================
- Practice Git exclusively from the command line for a while, even if you normally use a GUI — this builds a much deeper mental model of what's actually happening (staging, commits, refs) than clicking buttons does.
- Deliberately create a merge conflict (open the same file on two branches, edit the same line differently, then try to merge) and practice resolving it manually — most developers only learn this under real pressure otherwise.
- Read the commit history of a well-maintained open-source project — notice how experienced teams write commit messages and structure PRs.
- Practice `git rebase -i` (interactive rebase) to clean up messy commit history in a personal project before understanding it matters in a real team setting.
- Set up GitHub Actions for one of your own projects (even something simple like auto-running tests on every push) — this hands-on experience with CI/CD is a strong practical and interview-relevant skill.
- Contribute to a small open-source project — the real-world PR review process teaches Git collaboration skills that solo projects never expose you to.
- Review your own old commit messages critically — if you can't tell what a commit did from its message alone, practice writing clearer, more descriptive ones going forward.

=====================================================
12. COMMON MISTAKES AND HOW TO AVOID THEM
=====================================================
- Committing directly to `main`/`master` instead of using feature branches and PRs — even for solo projects, practicing proper branching builds the right habits early.
- Writing vague commit messages ("fix", "update", "stuff") instead of clear, descriptive ones explaining what changed and why.
- Committing secrets (API keys, passwords, `.env` files) — always set up `.gitignore` before your first commit in a new project.
- Using `git push --force` on a shared branch without understanding it overwrites others' history — extremely disruptive to teammates; use `--force-with-lease` and only when truly necessary.
- Making huge, sprawling commits that mix unrelated changes — makes history hard to read and makes reverting a specific change difficult.
- Not pulling the latest changes before starting new work — leads to avoidable, messy merge conflicts.
- Panicking and deleting a repository/branch when something goes wrong instead of learning to safely inspect and recover using `git reflog` (which tracks nearly everything, even after a reset).

=====================================================
13. CAREER GROWTH & STAYING CURRENT
=====================================================
- As you grow more senior, you'll increasingly be expected to define or refine your team's Git workflow/branching strategy, not just follow it — understanding the trade-offs between different workflows (Git Flow vs trunk-based, merge vs rebase) becomes a practical leadership skill.
- Git itself is stable and doesn't change dramatically, but GitHub's platform features (Actions, Copilot integrations, security scanning) evolve regularly — it's worth periodically checking GitHub's changelog for new features relevant to your workflow.
- Strong Git hygiene (clear commits, small focused PRs, good documentation) is one of the most consistently valued "soft technical" skills across every engineering team, regardless of language or stack — it's a durable investment.
